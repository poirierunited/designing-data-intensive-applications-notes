🔑 El Trade-off Fundamental de Índices

La base de datos más simple que puede existir es un archivo de texto donde agregas registros al final:

#!/bin/bash
# La DB más simple del mundo
db_set() { echo "$1,$2" >> database.txt; }
db_get() { grep "^$1," database.txt | tail -n 1 | cut -d',' -f2; }

db_set "user:1" '{"name":"Alex","role":"dev"}'
db_set "user:1" '{"name":"Alex","role":"senior dev"}'  # update = append
db_get "user:1"  # retorna la última versión

Escritura: O(1) — siempre al final. Lectura: O(n) — scan de todo el archivo. Esto escala terriblemente para lecturas.

Los índices resuelven el problema de lectura — estructuras adicionales que derivamos de los datos principales para acelerar queries. El trade-off es universal e inevitable:

Trade-off fundamental de índices: Los índices aceleran lecturas pero enlentecen escrituras. Cada escritura debe actualizar el dato Y todos sus índices. No hay índice gratis — solo elegís cuánta penalización de escritura aceptás por velocidad de lectura. Por eso no se indexa todo por default.

🗄️ Hash Indexes — El Índice más Simple

Solución de Bitcask (storage engine de Riak): un hash map en memoria donde cada clave mapea al byte offset en el archivo de datos donde está el valor.

Compaction y Merging de Segmentos

Con el tiempo, el log crece indefinidamente. Solución: dividir en segmentos de tamaño fijo. Cuando un segmento está lleno, se compacta en background:

  • Compaction: dentro de un segmento, descarta duplicados — solo mantiene el valor más reciente por clave
  • Merging: combina múltiples segmentos compactados en uno solo (merge sort por clave)
  • Mientras se mergea, las lecturas van al segmento viejo; cuando termina, se switcha al nuevo

Detalles de implementación reales

  • Tombstones: para borrar una clave, se escribe un marcador especial. En el merging, el tombstone descarta versiones anteriores
  • Crash recovery: al reiniciar, reconstruir el hash map escaneando todos los segmentos sería lento. Bitcask guarda snapshots del hash map en disco periódicamente
  • Escrituras parciales: si cae el proceso a mitad de una escritura, el registro queda corrupto. Bitcask usa checksums para detectar registros corruptos
  • Concurrencia: solo un writer (append-only es inherentemente secuencial); múltiples readers son seguros

¿Por qué append-only en lugar de actualizar en-lugar?

  • Escrituras secuenciales son mucho más rápidas que escrituras aleatorias en disco (HDD especialmente, pero también SSD)
  • Recovery más simple — si hay crash, el log muestra el estado exacto
  • Merging elimina fragmentación
Limitación crítica del Hash Index: todas las claves deben caber en RAM. Si tienes más claves que memoria, no funciona. Tampoco soporta range queries eficientes: "dame todos los usuarios con age entre 20 y 30" requiere escanear todo el hash.

📊 SSTables — Sorted String Tables

Una mejora simple pero poderosa sobre el log con hash index: ordenar los pares key-value dentro de cada segmento. Esto requiere que las escrituras se ordenen antes de escribir al disco (no se puede hacer append-only directamente).

Ventajas de tener las claves ordenadas

  • Merging eficiente: igual a mergesort — dos punteros, O(n) en total
  • Índice en memoria disperso: no necesitas guardar todos los offsets en memoria, solo uno cada ~kilobyte. Para buscar "dog", buscás entre "cat" y "fox" en disco
  • Compresión: un bloque entre dos entradas del índice puede comprimirse — menos I/O
  • Range queries: "dame todas las claves entre 'cat' y 'fox'" — search en índice + scan secuencial. ¡Resuelve la limitación del hash index!

🌲 LSM-Trees — Log-Structured Merge-Tree

LSM-Tree combina SSTables con una estructura en memoria: el memtable. Usado por LevelDB, RocksDB, Cassandra, HBase, y muchos más.

Flujo detallado de escritura en LSM

  1. La escritura va al WAL (Write-Ahead Log) en disco — para recuperación ante crash
  2. También se inserta en el memtable (un balanced tree en RAM: Red-Black tree, AVL)
  3. El memtable tiene orden automático (es un BST), así que cuando se llena (~4MB), se escribe al disco como un SSTable ordenado
  4. En background, el proceso de compaction merge-sortea SSTables para producir SSTables más grandes y ordenados

Lectura en LSM

Para leer una clave: busca en memtable → SSTable L0 más reciente → L0 más antiguo → L1 → L2… Puede ser lento si la clave no existe. Solución: Bloom filters — una estructura probabilística que te dice con certeza cuando una clave NO está en un SSTable (puede dar falsos positivos, nunca falsos negativos). Esto evita buscar en SSTables que definitivamente no tienen la clave.

Size-tiered vs Leveled Compaction

Size-tiered (Cassandra default)
  • SSTables nuevos y pequeños se mergean con los existentes del mismo tamaño
  • Menor write amplification
  • Más espacio en disco (datos antiguos y nuevos coexisten)
  • Lecturas más lentas (más SSTables a revisar)
Leveled (LevelDB / RocksDB default)
  • Las claves se dividen en rangos; cada key solo existe en 1 SSTable por level
  • Mayor write amplification (un dato puede escribirse muchas veces)
  • Menos espacio en disco
  • Lecturas más predecibles

🌳 B-Trees — El Estándar de la Industria

Los B-Trees son la estructura de índice más utilizada en bases de datos relacionales (PostgreSQL, MySQL, Oracle). A diferencia de LSM-trees que tratan el disco como un log, los B-Trees dividen el disco en páginas de tamaño fijo (típicamente 4KB).

Escritura en B-Trees

Para actualizar un valor: encuentra la página hoja, modifica el valor in-place, escribe la página de vuelta. Para agregar una clave nueva: si la página tiene espacio, agrega. Si no, split de la página en dos y actualiza el padre.

Durabilidad: Write-Ahead Log (WAL)

Si el DB cae mientras está en mitad de un split de página, el árbol queda en estado inconsistente. Solución: antes de cualquier modificación al B-tree, escribe la operación al WAL (redo log). Al recuperarse del crash, replaya el WAL para llegar a un estado consistente. Esto añade escrituras pero garantiza durabilidad.

Variante: copy-on-write (LMDB). En lugar de modificar páginas in-place + WAL, escribe una nueva versión de la página en otro lugar y actualiza el puntero del padre atómicamente. No necesita WAL; más simple de razonar sobre concurrencia y snapshots.

⚔️ B-Trees vs LSM-Trees — La Comparación Real

LSM-Trees (LevelDB, RocksDB, Cassandra)
  • ✓ Mejor throughput de escritura (solo append sequencial)
  • ✓ Mejor compresión (sin fragmentación interna)
  • ✓ Menor write amplification en workloads de alta escritura
  • ✗ Compaction puede interferir con I/O de lecturas activas
  • ✗ Una clave puede existir en múltiples SSTables — locks más complejos
  • ✗ Read latency menos predecible
B-Trees (PostgreSQL, MySQL, Oracle)
  • ✓ Read latency predecible (profundidad del árbol = log N hops)
  • ✓ Cada clave existe exactamente en un lugar → transacciones más simples
  • ✓ Madurez: décadas de optimizaciones
  • ✗ Write amplification mayor (WAL + página misma)
  • ✗ Fragmentación interna (páginas medio vacías después de deletes)
  • ✗ Menos compresión efectiva
Write Amplification: cuando escribís 1 byte de datos, cuántos bytes termina escribiendo el storage engine en disco. En B-Trees: escribís al WAL + a la página. En LSM: el mismo dato puede ser reescrito múltiples veces durante compaction. En SSDs, cada write cycle desgasta el chip — write amplification importa para la vida útil.

¿Cuándo elegir cada uno?

  • Alta escritura, tiempo real: LSM (Cassandra para IoT, logs, time-series)
  • Lecturas predecibles, transacciones: B-Tree (PostgreSQL para e-commerce, financial)
  • General purpose: InnoDB (MySQL) y PostgreSQL usan B-Trees y son la opción sólida por default

🔍 Otros Tipos de Índices

Índices secundarios

Los índices primarios indexan por la primary key. Los secundarios indexan por otro campo. En PostgreSQL: CREATE INDEX ON orders(customer_id). Las claves no son únicas en índices secundarios — múltiples filas pueden tener el mismo customer_id. Se resuelve guardando una lista de row IDs o haciendo la clave única agregando el row ID.

Clustered vs Non-clustered Indexes

  • Clustered: los datos de la fila se guardan directamente en el índice (no hay un salto adicional). El índice IS el almacenamiento. InnoDB siempre usa clustered index en la primary key.
  • Non-clustered: el índice solo guarda punteros a las filas reales (heap file). Una lectura = buscar en el índice + buscar en el heap. Más lento, pero más flexible.
  • Covering index: incluye columnas adicionales en el índice para que algunos queries se satisfagan solo con el índice, sin leer el heap. Trade-off: más espacio.

Multi-column indexes

Un índice sobre (last_name, first_name) permite queries eficientes en last_name, o en last_name + first_name, pero NO solo en first_name. El orden importa. Para queries geoespaciales como "restaurantes cerca de mí" necesitas índices que soporten 2D: R-trees, space-filling curves (Cassandra usa Hilbert curve para localidad espacial).

Full-text e índices fuzzy

Lucene (base de Elasticsearch) usa una estructura similar a SSTables para buscar texto con tolerancia a typos. El índice mapea palabras → documentos. Búsqueda fuzzy mediante Levenshtein automata — permite encontrar "MercadoLibre" si escribís "MercadoLibrr".

In-memory databases: Si toda la data cabe en RAM, ¿por qué escribir al disco? Redis y Memcached son puramente in-memory. VoltDB, MemSQL ofrecen durabilidad escribiendo al disco en background. La ventaja no es velocidad de acceso (el OS cachea igual), sino eliminar la serialización a un formato compatible con disco.

📚 Glosario

Write Amplification
Ratio entre bytes escritos al disco vs bytes de datos originales. 1 byte de dato puede causar 10+ bytes de escritura en disco con compaction y WAL.
Memtable
Buffer de escrituras en RAM (balanced tree). Mantiene claves ordenadas. Cuando se llena (~4MB), se flushea a SSTable en disco.
SSTable
Sorted String Table. Archivo inmutable en disco con key-value ordenados. Base de los LSM-Trees. Mergeable eficientemente con merge sort.
Bloom Filter
Estructura probabilística que responde "la clave DEFINITIVAMENTE no está aquí" con 0% falsos negativos. Evita buscar en SSTables innecesariamente.
WAL
Write-Ahead Log. Log append-only donde se registran todas las operaciones ANTES de ejecutarlas. Permite recovery ante crashes. Usan B-Trees y LSM.
Compaction
Proceso background de LSM: merge de SSTables para eliminar versiones antiguas, reducir espacio y mejorar performance de lectura. Compite con I/O de queries activos.
Branching Factor
Número de hijos por nodo en un B-Tree. Típicamente 100-200. Con 4 niveles: 200^4 = 1.6 billones de registros indexables. Determina la altura del árbol.
Covering Index
Índice que incluye todas las columnas de un query, evitando el salto al heap. "Index-only scan" en PostgreSQL. Más espacio, lecturas más rápidas.
