📈 Escalabilidad: Describiendo la Carga

Escalabilidad no es una propiedad binaria — no existe "esto escala". Es una pregunta concreta: "si mi carga aumenta de X forma, ¿cuáles son mis opciones?". Para responderla primero hay que describir la carga con parámetros precisos.

Load Parameters — El ejemplo de Twitter (2012)

Twitter tenía dos operaciones principales:

  • Post tweet: 4.600 req/seg promedio, pico 12.000 req/seg → fácil de manejar
  • Home timeline: 300.000 req/seg → aquí estaba el verdadero desafío

El problema no era el volumen de escritura — era el fan-out: cada usuario sigue a muchos y es seguido por muchos. Dos enfoques:

En MercadoLibre: Imagina el feed de actividad de un seller con millones de compradores. Si publicás un descuento y tenés que escribir en el feed de 2M usuarios, eso es exactamente el problema de fan-out. ML resuelve esto con una mezcla de eventos asincrónicos y caches pre-computados por segmento.

Twitter Híbrido — La solución real

La mayoría de los tweets siguen el Enfoque 2 (fan-out al publicar). Pero para usuarios con millones de seguidores (celebrities), se usa el Enfoque 1: sus tweets se buscan por separado y se mergean al leer el timeline. El parámetro clave: distribución de seguidores por usuario (no el promedio — el percentil importa).

📊 Describiendo el Rendimiento — Percentiles

¿Por qué no usar el promedio?

El promedio (media aritmética) no te dice cuántos usuarios realmente tuvieron esa experiencia. Si 99 usuarios esperan 100ms y 1 usuario espera 10 segundos, el promedio es ~200ms — pero ese 1 usuario está sufriendo.

Percentiles: la métrica correcta

  • p50 (mediana): la mitad de los requests son más rápidos que esto. Si p50 = 200ms, 50% de usuarios ven ≤200ms
  • p95: 95% de requests son más rápidos. El 5% peor caso
  • p99: 99% de requests son más rápidos. Solo el 1% es más lento
  • p999 (tail latency): el 0.1% más lento. Amazon lo usa internamente

Tail Latency Amplification

Cuando un request del usuario requiere llamar a N microservicios en paralelo, la latencia total es la del más lento. Si cada servicio tiene p99 = 1s, y llamas a 5 servicios en paralelo:

P(al menos uno ≥ 1s) = 1 - (0.99)^5 ≈ 5% de requests del usuario verán ≥1s — aunque individualmente parezca "solo el 1%"

En ML, cada página de producto podría llamar a: pricing service, inventory, reviews, recommendations, shipping cost. Si cada uno tiene p99=500ms y fallas independientes, el usuario final sufre degradación mucho más seguido de lo que esperarías.

SLAs y SLOs — Contratos de rendimiento

  • SLO (Service Level Objective): meta interna — "queremos p99 < 500ms"
  • SLA (Service Level Agreement): contrato con el cliente — si no se cumple, hay penalidad económica
  • Amazon fija internamente sus SLAs en p999 — los clientes más lentos suelen tener más datos y son los más valiosos
  • Amazon midió: +100ms de latencia → -1% en ventas

⚖️ Cómo Afrontar el Crecimiento de Carga

Scale Up vs Scale Out

Sistemas Elásticos

Un sistema elástico detecta aumento de carga y agrega recursos automáticamente (auto-scaling). Uno escalado manualmente tiene un humano que analiza y decide. Los sistemas manuales son más simples y predecibles; los elásticos son clave cuando la carga es impredecible.

No hay "magic scaling sauce" — la arquitectura que funciona para 100k req/seg de 1KB cada uno es completamente diferente a la que funciona para 3 req/min de 2GB. Todo depende del patrón de acceso: volumen de reads, writes, tamaño de datos, complejidad, latencia requerida.

Stateless vs Stateful

Distribuir servicios stateless es simple — cualquier nodo puede manejar cualquier request. Distribuir sistemas stateful (bases de datos) introduce complejidad enorme: consistencia, particionado, replicación. Por eso el consejo clásico fue: mantén la DB en un solo nodo hasta que el costo o disponibilidad te fuercen a distribuirla. Los capítulos 5-9 del libro atacan justamente esta complejidad.

🔧 Mantenibilidad — El costo real del software

La mayor parte del costo del software no es desarrollo inicial — es mantenimiento continuo: bugs, adaptación a nuevas plataformas, deuda técnica, nuevas features. El objetivo es diseñar sistemas que sean un placer de mantener, no legado doloroso.

Tres principios de diseño:

1. Operability — Hacer la vida fácil a ops

Un sistema operable permite que el equipo de operaciones haga su trabajo sin fricción. Un buen equipo de ops:

  • Monitorea la salud del sistema y restaura servicio cuando falla
  • Rastrea la causa raíz de fallas o degradaciones
  • Mantiene plataformas al día (patches de seguridad) sin downtime
  • Anticipa problemas futuros y los previene (capacity planning)
  • Establece buenas prácticas para deployment y configuración
  • Preserva el conocimiento del sistema — documentación, runbooks
Buen software de operabilidad: visibilidad del estado interno, soporte para automatización, evitar dependencias en máquinas individuales, comportamiento predecible y documentado.

2. Simplicity — Eliminar complejidad accidental

Hay dos tipos de complejidad:

  • Complejidad esencial: inherente al problema que estás resolviendo
  • Complejidad accidental: la que el sistema introdujo innecesariamente — state explosion, coupling inconsistente, naming inconsistente, hacks sobre hacks

La herramienta más poderosa contra la complejidad accidental es la abstracción: encapsular detalles de implementación detrás de una interfaz limpia. Por ejemplo:

  • SQL es una abstracción sobre B-trees + join algorithms + storage
  • Un lenguaje de alto nivel es una abstracción sobre instrucciones de CPU
  • TCP es una abstracción sobre paquetes IP y routing

Una buena abstracción oculta toneladas de complejidad accidental y puede ser reutilizada. El libro busca identificar abstracciones que permiten extraer partes de sistemas distribuidos en componentes reutilizables.

3. Evolvability — Facilitar cambios futuros

Los requisitos siempre cambian: nuevos casos de uso, regulaciones, mercados, bugs en el modelo de negocio. La capacidad de modificar un sistema fácilmente a medida que se entiende mejor el problema es crucial. También conocida como extensibilidad, modifiabilidad o plasticidad.

Agilidad a nivel de sistema de datos — En código, Agile y TDD facilitan el cambio. A escala de sistema de datos, los conceptos clave son: patrones de diseño simples, buenas abstracciones, desacoplamiento de componentes. Lo que el libro busca explorar en los próximos capítulos.

📚 Glosario Clave

Load Parameter
Número que describe la carga del sistema: req/seg, ratio reads/writes, usuarios activos, hit rate de cache. La elección correcta depende de la arquitectura.
Fan-out
Número de requests a otros servicios para atender 1 request del usuario. En Twitter: 1 tweet → N escrituras en timelines de seguidores.
Tail Latency
Latencia en percentiles altos (p95, p99, p999). Los "outliers" de respuesta lenta que afectan a usuarios con mucha actividad — los más valiosos.
Head-of-line Blocking
Un request lento bloquea la cola de requests rápidos que vienen detrás. Amplifica la latencia percibida.
Shared-Nothing
Arquitectura horizontal donde cada nodo es independiente. No comparten memoria ni disco. Requiere coordinación explícita.
Accidental Complexity
Complejidad que el sistema introdujo innecesariamente — no inherente al problema. Abstracciones bien diseñadas la eliminan.
SLA / SLO
SLO: objetivo interno de performance. SLA: contrato con el cliente con penalidades si no se cumple.
Elastic Scaling
Sistema que agrega/quita recursos automáticamente según demanda detectada. Opuesto: escalado manual por decisión humana.
