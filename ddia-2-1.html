El Cap.1 estableció que los sistemas de datos deben ser confiables (tolerar fallas hardware/software/humanas), escalables (afrontar crecimiento con parámetros de carga bien definidos — percentiles, no promedios; fan-out; tail latency) y mantenibles (operability, simplicity por abstracciones, evolvability). Ahora entramos al Cap.2: ¿cómo organizamos y representamos los datos mismos?

🗂️ El Nacimiento de NoSQL

En 2009 apareció el hashtag #NoSQL en Twitter para una conferencia de bases de datos open source. El nombre quedó, aunque no explica nada técnicamente — "Not Only SQL" fue el backrónimo posterior. Lo que impulsó el movimiento fue una combinación de factores reales:

  • Necesidad de mayor escala de la que SQL tradicional permitía fácilmente
  • Cargas de escritura muy altas (analytics en tiempo real)
  • Esquemas más flexibles — requirements que cambiaban rápidamente
  • Operaciones especializadas que el modelo relacional no soporta bien
  • Frustración con el modelo relacional restrictivo para ciertos dominios

El modelo relacional (Codd, 1970) dominó por décadas. NoSQL no lo reemplaza — complementa para casos donde el modelo relacional no es el más natural. Hoy conviven ambos en producción.

🧩 Impedance Mismatch — El problema de fondo

Si usas orientación a objetos en código (Python, Go, Node.js) y guardas en SQL relacional, hay una brecha entre modelos: objetos tienen jerarquías, arrays, herencia — tablas tienen filas y columnas planas. Esta brecha se llama impedance mismatch.

El ejemplo del CV (perfil de usuario)

Un perfil de usuario típico tiene: nombre, varios puestos de trabajo (cada uno con empresa, cargo, fechas), varias posiciones geográficas históricas, skills, educación. En SQL relacional:

El modelo documental es mejor para one-to-many (un usuario tiene muchos jobs). Las ORMs (ActiveRecord, Hibernate) mitigan parte del impedance mismatch, pero no lo eliminan — solo ocultan el boilerplate.

🔗 Relaciones: Many-to-One y Many-to-Many

¿Por qué normalizar?

Si guardas "industria: Tecnología" como string en cada perfil, y alguien escribe "tecnología" en minúscula o "Tech", tienes inconsistencias. Mejor: un ID numérico que referencia una tabla de industrias. Esto es normalización — eliminar duplicación, mantener consistencia.

La tensión fundamental: el modelo documental es bueno para one-to-many pero malo para many-to-many. El modelo relacional es bueno para many-to-many (JOINs) pero introduce impedance mismatch con el código OO. No hay respuesta universal.

Ejemplo: Recomendaciones entre usuarios

En LinkedIn, un usuario puede recomendar a otro usuario — ambos tienen perfiles en la base de datos. Esto es many-to-many: muchos usuarios recomiendan a muchos usuarios. En un documento JSON anidado, ¿cómo referencias a otro usuario? Necesitas su ID y hacer otro query — que es básicamente un JOIN manual.

📜 Historia de los Modelos de Datos

IMS (1968) — El modelo jerárquico

IBM's Information Management System usaba un árbol de registros — como JSON anidado pero sin flexibilidad. Bueno para one-to-many, imposible para many-to-many. Si un estudiante cursa varias materias y una materia tiene varios estudiantes — no hay forma natural de representarlo en un árbol.

CODASYL (años 70) — El modelo de red

Propuesto como solución al problema de many-to-many del IMS. Un registro podía tener múltiples padres. Los programmers navegaban los datos siguiendo punteros manualmente (el "programador como navegador" — Bachman, 1973). Extremadamente poderoso pero terrible de usar: había que saber el access path exacto, migrar el esquema era un nightmare.

Modelo Relacional (Codd, 1970)

La idea radical: simplemente colecciones de tuplas (filas). Sin punteros, sin access paths. El query optimizer decide cómo ejecutar — el developer solo declara qué quiere, no cómo obtenerlo. Parecía impráctica en 1970 (¿sin punteros?), pero cuando IBM implementó DB2 y Oracle apareció, demostró ser mucho más simple de usar y el rendimiento alcanzó al modelo de red.

⚡ Schema-on-Write vs Schema-on-Read

Schema-on-Write (SQL / Relacional)

El esquema se define explícitamente antes de insertar datos. La base de datos enforcea el esquema en cada escritura. Como la tipificación estática en código: si intentás insertar un string donde va un int, falla antes.

  • Ventaja: garantías fuertes — sabés exactamente qué estructura tienen tus datos
  • Desventaja: ALTER TABLE en una tabla con millones de filas puede tardar horas y bloquear la tabla

Schema-on-Read (MongoDB / Documental)

La base de datos no enforcea ningún esquema. Cualquier documento puede tener cualquier estructura. El esquema está implícito — el código que lee los datos asume la estructura. Como tipificación dinámica en Python.

  • Ventaja: flexibilidad total — podés cambiar la estructura de documentos nuevos sin tocar los viejos
  • Desventaja: el schema está ahora en el código de la aplicación, esparcido en múltiples lugares
Schema-on-read NO significa "sin schema" — significa schema implícito, asumido por el código. Si tu colección de usuarios tiene documentos con first_name y otros con firstName, tienes un esquema implícito inconsistente. Eso es peor que un esquema explícito.

¿Cuándo usar cada uno?

Schema-on-read brilla cuando tienes items de tipos heterogéneos que es complicado poner en la misma tabla, o cuando la estructura de los datos la controla una parte externa y puede cambiar en cualquier momento (APIs de terceros). Schema-on-write es mejor cuando todos los items tienen la misma estructura y sabes exactamente qué estructura necesitas.

En ML: Los datos de productos en ML son naturalmente heterogéneos — un auto tiene cilindros, un libro tiene ISBN, una ropa tiene talla. MongoDB o esquemas flexibles en SQL (JSONB en PostgreSQL) encajan mejor que una tabla plana con 300 columnas, la mayoría NULL.

📍 Localidad de Datos y Queries Declarativas

Data Locality

En un documento, todos los datos relacionados están juntos. Si querés mostrar el perfil completo de un usuario, un solo read del disco te da todo. En el modelo relacional con 5 tablas normalizadas, el DB engine necesita buscar en múltiples lugares del disco.

Esto importa cuando necesitas grandes partes del documento a la vez. Si solo necesitas el nombre del usuario, cargar el documento completo con todos sus jobs y skills es ineficiente — Spanner y Cassandra ofrecen locality a nivel de row dentro de una tabla relacional.

SQL Declarativo vs Imperativo (MapReduce)

-- SQL: DECLARATIVO — describes QUÉ quieres
SELECT species, COUNT(*) as count
FROM animals
WHERE family = 'Sharks'
GROUP BY species;
-- Equivalente imperativo en JavaScript:
var counts = {};
animals.forEach(a => {
  if (a.family === 'Sharks') {
    counts[a.species] = (counts[a.species] || 0) + 1;
  }
});
// El optimizer NO puede reordenar tu código

SQL declarativo permite que el query optimizer elija el mejor execution plan: qué índice usar, qué orden de JOINs, si paralelizar. Tu código imperativo está atado a la forma en que lo escribiste.

MapReduce es un caso intermedio — ni puramente declarativo ni puramente imperativo. La función map y reduce son código que el developer escribe, pero el framework decide cómo distribuirlo. MongoDB ofrece una aggregation pipeline que es más declarativa que MapReduce.

// MongoDB aggregation pipeline
db.animals.aggregate([
  { $match: { family: "Sharks" } },
  { $group: { _id: "$species", count: { $sum: 1 } } }
]);
CSS también es declarativo — describes cómo se ve, no cómo el browser calcula los píxeles. Si fuera imperativo tendrías que calcular coordenadas tú mismo. La misma potencia del enfoque declarativo.

📚 Glosario

Impedance Mismatch
Brecha entre el modelo de objetos en código (OO) y el modelo relacional en DB. ORMs reducen el boilerplate pero no eliminan la incompatibilidad conceptual.
Normalización
Eliminar duplicación representando datos como ID que referencian una fuente única. Hace updates consistentes pero requiere JOINs para leer.
Schema-on-Write
El esquema se enforcea al escribir. SQL relacional. Garantías fuertes, ALTER TABLE costoso en prod.
Schema-on-Read
El esquema está implícito, interpretado al leer. MongoDB. Flexibilidad, pero el schema vive en el código de la aplicación.
Data Locality
Datos relacionados físicamente cercanos en disco. Documentos tienen alta localidad. Reduce I/O cuando necesitás el documento completo.
ORM
Object-Relational Mapping. Hibernate, ActiveRecord, Prisma. Abstrae el SQL pero introduce su propia complejidad (N+1 queries, lazy loading).
Fan-out (modelo)
En modelos de datos: cuántas tablas/documentos hay que leer para satisfacer 1 query. Alta en relacional normalizado, baja en documentos.
Query Optimizer
Componente del DB que decide el plan de ejecución de un query SQL. Puede elegir índices, orden de JOINs, paralelismo — sin que el developer lo especifique.
